# Answer Key — Practice Test 1

**Q1. Correct: B**

IaC written declaratively and stored in version control ensures every environment is provisioned from the same source of truth, eliminating the drift caused by manual, undocumented changes.

---

**Q2. Correct: B**

Terraform Core is provider-agnostic; provider plugins translate a single HCL workflow (init/plan/apply) into calls against each platform's API, enabling true multi-cloud and hybrid-cloud management.

---

**Q3. Correct: B**

Storing infrastructure definitions as code in Git provides commit history, peer review, and rollback capability — giving repeatable and auditable changes, a core IaC benefit over wiki-based documentation.

---

**Q4. Correct: A**

IaC's foundational purpose is to replace manual, ad-hoc, inconsistent infrastructure provisioning with declarative, version-controlled, repeatable processes.

---

**Q5. Correct: D**

Terraform's HCL is declarative — you describe the desired end state, and Terraform's engine builds a resource graph to determine dependency order automatically. `terraform plan` generates an execution plan showing exactly what will be created, changed, or destroyed before any action is taken.

---

**Q6. Correct: B**

Terraform excels at provisioning cloud infrastructure resources and tracking their real-world state in a state file, enabling create/update/destroy planning. Ansible excels at configuration management — installing packages, managing files, and configuring software on already-provisioned hosts. Using each tool for its strength is the standard complementary pattern.

---

**Q7. Correct: B**

Terraform builds a directed acyclic graph (DAG) from resource and data source dependencies in the configuration. This graph lets Terraform determine which resources are independent (and can be processed in parallel) and which must wait on others, ensuring operations happen in a safe, correct order.

---

**Q8. Correct: D**

`terraform plan` compares the current state against the configuration and desired state, then outputs a detailed execution plan showing which resources will be added, changed, or destroyed — without making any actual changes.

---

**Q9. Correct: B**

The pessimistic constraint operator ~> 5.10.0 (three-part version) locks the rightmost segment, allowing only patch releases within 5.10.x (5.10.1, 5.10.2, etc.) while blocking 5.11.0 or higher.

---

**Q10. Correct: B**

The dependency lock file is generated by terraform init and records the specific provider versions and cryptographic checksums that satisfy the required_providers constraints, guaranteeing everyone on the team gets the same provider builds.

---

**Q11. Correct: C**

Provider aliases let you define multiple configurations of the same provider (e.g., different regions) in one configuration; resources opt into the non-default configuration with the provider meta-argument, such as provider = aws.eu_west.

---

**Q12. Correct: A**

Terraform state is the source of truth that maps configuration blocks to actual infrastructure objects, tracks metadata and dependencies, and lets Terraform avoid querying every resource's full attributes on every run — critical for performance at scale.

---

**Q13. Correct: C**

required_providers must live inside the terraform block, and each provider entry is an object with source and version keys, exactly as shown in option C — this is the syntax Terraform expects to resolve and lock the provider.

---

**Q14. Correct: D**

By default terraform init respects the existing lock file. If the locked version no longer satisfies an updated version constraint, init errors out and instructs the user to run terraform init -upgrade to select and record a new compatible version.

---

**Q15. Correct: D**

The `-/+` prefix in plan output means destroy-then-create replacement — the resource cannot be updated in place because a changed attribute forces recreation.

---

**Q16. Correct: A**

terraform validate checks syntax and internal consistency (e.g., argument types, references) using only the local configuration and cached provider schema; it does not need network or backend access.

---

**Q17. Correct: B**

terraform init -upgrade re-evaluates version constraints and installs the latest provider and module versions permitted by the configuration, updating the lock file accordingly.

---

**Q18. Correct: D**

Some attributes are defined by the provider schema as requiring resource replacement (ForceNew) because the underlying cloud API doesn't support updating that attribute in place — availability_zone on an EC2 instance is a classic example.

---

**Q19. Correct: B**

Terraform constructs a dependency graph from resource references and explicit depends_on relationships, then walks the graph to determine which operations can run in parallel and which must be sequenced.

---

**Q20. Correct: D**

terraform destroy -target=<address> actually destroys the specified resource in real infrastructure while leaving all other resources untouched, allowing it to be recreated on the next apply.

---

**Q21. Correct: C**

Terraform provider schemas mark certain attributes as requiring replacement (commonly labeled ForceNew internally, shown as '# forces replacement' in plan output). subnet_id for aws_instance is one such attribute — AWS does not support changing the subnet of a running EC2 instance, so the only way to apply the change is to destroy the existing instance and create a new one in the target subnet. The plan output explicitly annotates this with the 'forces replacement' comment next to the changed line.

---

**Q22. Correct: A**

Input variable custom validation requires a validation block nested inside the variable block, and that block must contain exactly two arguments: condition (a boolean expression) and error_message (the string shown when condition is false).

---

**Q23. Correct: D**

for_each keys resources by a stable identifier (map key or set element) rather than a numeric index. Converting the list to a set with toset() and using for_each = toset(var.user_names) means each resource instance is tracked by its name value, so removing one name only destroys that specific instance — the others are unaffected.

---

**Q24. Correct: D**

To generate a variable number of nested configuration blocks (like ingress inside aws_security_group), Terraform requires a dynamic block. The block is named after the nested block type being generated (dynamic "ingress"), takes for_each to iterate the list, and uses a content block that references each element via the iterator's default name (ingress.value.<attribute>).

---

**Q25. Correct: A**

A precondition inside a lifecycle block is evaluated before the resource is created or updated. If the condition expression evaluates to false, Terraform halts with an error displaying the specified error_message, preventing the apply from proceeding for that resource (and any dependents).

---

**Q26. Correct: A**

Marking an output (or variable) sensitive only affects Terraform's CLI display behavior — the value is hidden/redacted (shown as (sensitive value)) in plan, apply, and console output. It does not encrypt or remove the value from the state file; the raw value is still persisted in plain text in terraform.tfstate, which is why state files must be protected via a secure backend and access controls.

---

**Q27. Correct: A**

When two resources have a dependency that Terraform cannot infer from resource attribute references (no interpolation from one to the other), an explicit depends_on argument must be added to force the correct ordering. depends_on = [aws_iam_policy.example] tells Terraform to always create/update aws_iam_policy.example before the aws_instance resource, regardless of attribute references.

---

**Q28. Correct: C**

Postconditions live in a lifecycle block and are evaluated after the data source is read (or after a resource is created/updated), making them the correct tool to validate the actual returned value, such as a tag on a fetched AMI, and fail with a custom_condition error message if it doesn't meet expectations.

---

**Q29. Correct: A**

The pessimistic constraint operator ~> 3.0 (with two version segments) allows only the rightmost component to increment, permitting 3.0.1, 3.0.2, etc., but excluding 3.1.0 or 4.0.0 — exactly patch-only updates.

---

**Q30. Correct: C**

The generic git:: source prefix with an explicit ssh:// protocol tells Terraform to clone the repository using the local SSH configuration, which is required when HTTPS access is not set up for a private repo.

---

**Q31. Correct: A**

The version argument is only meaningful for registry-hosted modules, which publish semantic version metadata; Terraform uses it to resolve a matching published version.

---

**Q32. Correct: C**

Outputs exported by a child module are referenced from the calling module using module.<MODULE_NAME>.<OUTPUT_NAME>, where MODULE_NAME matches the label used in the module block.

---

**Q33. Correct: D**

Passing module.network.environment_tier as the value for instance_class correctly references the network module's output, and Terraform automatically infers the dependency so network is applied before database.

---

**Q34. Correct: D**

Remote backends with locking (HCP Terraform, or S3 with its native conditional-write locking, or the older S3+DynamoDB pattern) prevent concurrent writes to state, which is exactly the corruption/conflict scenario described.

---

**Q35. Correct: C**

The `sensitive` attribute only redacts values from CLI plan/apply output and logs; the actual value is still stored in plaintext in the state file. Best practice is to store state in an encrypted, access-restricted remote backend.

---

**Q36. Correct: B**

HCP Terraform (Terraform Cloud) provides remote state storage with locking built in as part of the platform — no extra infrastructure needs to be configured by the user.

---

**Q37. Correct: C**

terraform state rm removes a resource from the state file only; the real-world object is untouched and Terraform no longer tracks it.

---

**Q38. Correct: C**

The `moved` block tells Terraform that a resource's address changed, so it updates the state mapping in place instead of destroying and recreating the resource.

---

**Q39. Correct: A**

State is the source of truth Terraform uses to map declared resources in configuration to actual objects in the real world, tracking IDs, attributes, and dependency ordering between applies.

---

**Q40. Correct: B**

Variable sets let you define a group of variables (including sensitive ones) once and attach them to multiple workspaces or an entire project, avoiding duplication and easing updates.

---

**Q41. Correct: A**

Sentinel is HashiCorp's proprietary policy-as-code framework built into HCP Terraform (available in higher tiers), used alongside the OPA integration to enforce advisory, soft-mandatory, or hard-mandatory policies before applies.

---

**Q42. Correct: C**

Dynamic provider credentials let HCP Terraform generate short-lived credentials at run time via OIDC federation with the cloud provider, eliminating the need to store static long-lived secrets.

---

**Q43. Correct: C**

Run triggers connect a source workspace to one or more downstream workspaces so that a successful apply in the source automatically queues a plan/run in the linked workspace, enabling dependency chaining across workspaces.

---

**Q44. Correct: D**

Drift detection schedules periodic speculative plans on workspaces to compare real infrastructure against the last-known state and surface any out-of-band changes, without applying anything automatically.

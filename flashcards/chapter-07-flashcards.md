## Chapter 7: Writing HCL: Types, Loops, Validation & Sensitive Data — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | count vs for_each: what happens when you remove a middle element from the input? | count: shifts all subsequent numeric indices, causing destroy/recreate of every resource after the removed index. for_each: only the resource tied to that specific map/set key is destroyed — others are unaffected. Exam tip: for_each is preferred when items can be added/removed independently. |
| 2 | What input types does for_each accept? | A map or a set of strings only — not a list. Convert a list with toset(list) if you need for_each over list values. Exam tip: using a plain list on for_each directly throws an error. |
| 3 | dynamic block — what is it for? | Generates repeated nested configuration blocks (like ingress/egress rules) inside a single resource by iterating over a list/map, using a content { } block and an implicit iterator (default name matches the block label, or use iterator = custom_name). |
| 4 | merge() function syntax and override behavior | merge(map1, map2, ...) — combines maps into one; when a key exists in multiple maps, the value from the last (rightmost) map wins. |
| 5 | lookup() function syntax | lookup(map, key, default) — returns map[key] if present, otherwise returns default, avoiding an error on a missing key. |
| 6 | join() function syntax | join(separator, list) — concatenates a list of strings into a single string using the given separator. Inverse of split(). |
| 7 | Complex type: tuple vs object — key difference | tuple([type1, type2, ...]) is an ordered, fixed-length sequence where each position can have a different type, accessed by index. object({attr = type, ...}) is a structured type with named attributes, each with its own type, accessed by name. Exam tip: map requires all values share one type; object allows mixed types per named attribute. |
| 8 | Variable validation block — required arguments | condition (boolean expression referencing the variable) and error_message (string shown when condition is false). Placed inside the variable block. Runs at plan time before resources are evaluated. |
| 9 | precondition vs postcondition — when do they run? | Both live inside a lifecycle block on resource/data/output blocks. precondition is checked before the resource/data is evaluated; postcondition is checked after, validating the resulting attributes. Available since Terraform 1.2. |
| 10 | check block — purpose and structure | Introduced in Terraform 1.5. A top-level check block contains one or more assert { condition, error_message } blocks that validate ongoing infrastructure assumptions without blocking apply (failures produce warnings, not errors). |
| 11 | sensitive = true on a variable or output — what does it actually protect? | Redacts the value from CLI plan/apply output and console logs only. The value is still stored in plaintext in the Terraform state file — state must be secured separately (encrypted backend, restricted access). |
| 12 | Terraform + HashiCorp Vault — conceptual role | The vault provider's data sources fetch secrets dynamically at plan/apply time so secrets aren't hardcoded in config. However, retrieved values still land in Terraform state, so state protection remains a separate, required concern. |
